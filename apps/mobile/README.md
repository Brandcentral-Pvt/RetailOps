# RetailOps mobile — iOS & Android

One app, two surfaces. Internal RetailOps staff and seller clients share a
shell, a component library and a token set; what each person sees is decided by
`visibility = surface × permission × data scope`.

The design system this app implements lives in
[`docs/design/mobile/`](../../docs/design/mobile/README.md) — 140 screens, a
token file, a 48-rule consistency contract and a machine-readable registry.
**This app is generated from those files and cannot drift from them.**

> Working here for the first time? Read [`AGENTS.md`](./AGENTS.md) first. It is
> the short version of everything below, and it is binding.

---

## 1. Quick start

```bash
cd apps/mobile
npm install
npm run doctor     # verify wiring, ids and secrets before wasting a build
npm start          # then press a / i, or scan the QR with Expo Go
```

Requires Node 20.18+ (pinned in `eas.json`).

## 2. Daily commands

| Command | What it does | When |
|---|---|---|
| `npm start` | Expo dev server | |
| `npm run android` / `npm run ios` | Native run (needs a dev build — see §4) | |
| `npm run typecheck` | `tsc --noEmit`, strict | before every commit |
| `npm run tokens` | Regenerate `src/theme/tokens.generated.ts` | after editing the token file |
| `npm run scaffold` | Regenerate all 140 screens from the registry | after editing the screen inventory |
| `npm run lint:contract` | Enforce the consistency contract on app source | before every commit |
| `npm run doctor` | Cross-file wiring, secrets, platform ids | before a build |
| `npm run check` | typecheck + token sync + scaffold sync | in CI and before a PR |

The three `npm run tokens` / `scaffold` / `lint:contract` scripts are the
enforcement layer. A change that violates the design system fails in CI rather
than on a device.

## 3. Architecture

```
apps/mobile/src/
├── theme/          tokens.generated.ts (generated) + ThemeProvider
├── auth/           the visibility formula, session store, PermissionGate
├── nav/            destination registry, shell, screenRegistry.generated.ts
├── components/
│   ├── ui/         Text, Surface, Button, Chip, Skeleton — token-only
│   ├── states/     the nine interaction states
│   └── ScreenShell the frame every screen renders inside
├── screens/        140 generated screens, 8 groups (generated)
├── hooks/          useScreenData, useReducedMotion
└── services/       apiClient, authService, ApiError
```

Three decisions shape it:

1. **One app, two surfaces.** Two apps would double every token, component and
   bug fix. The surface comes from the session, not from the build.
2. **The registry is the product.** The bottom bar, the stacks, search and the
   More menu all read one filtered list. There is no separate admin menu.
3. **Generated, not written.** Screens and tokens are compiled from the design
   system. `npm run check` fails if either drifts.

### The nine states

Every screen composes from `components/states`: loading-first, loading-refresh,
empty-true, empty-filtered, error-recoverable, error-fatal, no-permission (403),
offline, stale-partial — plus selection, bulk, upload, conflict and rate-limited.
`ScreenShell` owns most of them; see `AGENTS.md` R3.

## 4. Building

Managed workflow. `ios/` and `android/` are gitignored and generated by EAS —
never commit them.

```bash
npx eas login
npx eas build --profile development --platform all   # internal dev build
npx eas build --profile preview     --platform all   # internal QA
npx eas build --profile production  --platform all   # store build
```

**`expo start` alone is not enough for a device.** `expo-dev-client` is in the
dependency set, so the app must be built at least once per device or simulator
before `npm run android` / `npm run ios` will work. Expo Go is not used.

`appVersionSource: remote` means EAS owns the build number; do not hand-edit
`version` to ship a build.

## 5. Configuration

| Variable | Purpose | Default |
|---|---|---|
| `EXPO_PUBLIC_API_URL` | API base | `https://data.brandcentral.in/api` |
| `EXPO_PUBLIC_SOCKET_URL` | Realtime base | `https://data.brandcentral.in` |
| `EXPO_PUBLIC_API_TIMEOUT` | Request timeout (ms) | `30000` |
| `EXPO_PUBLIC_USE_MOCKS` | Use mock data instead of the API | `false` |

Set locally in `apps/mobile/.env` (gitignored) or centrally in
`eas.json → build.base.env`. **There are no API secrets in the app** — the
token is a JWT held in `expo-secure-store`, never baked into the bundle.

## 6. Known gaps and decisions

Read these before assuming something is broken.

**B-1 · The login payload under-reports permissions.** Both `/auth/login` and
`/auth/me` return `permissions` straight from `RolePermissions`, but
`backend/middleware/auth.js` additionally applies each user's `ExtraPermissions`
and `ExcludedPermissions`. A user with a custom grant will see a bottom bar that
disagrees with what the server enforces, and will hit 403s the UI did not
predict. **Fix on the server**: apply the same extra/excluded merge in
`getResolvedUserResponse` (`backend/controllers/authController.js:17`) that the
middleware already does. Until then, this is a known, reproducible defect — not
an app bug.

**B-2 · Scope mode is mirrored, not delivered.** `scopeFor()` in
`authService.ts` re-derives scope from the role because no endpoint returns it.
**Fix**: have `/auth/me` return `scope: 'global' | 'assigned' | 'self'` and read
it. The single exempted role comparison then disappears.

**B-3 · `seller_client` does not exist in the backend.** 26 seller screens are
scaffolded against a role the system cannot yet authenticate, and
`05-role-ui-matrix.md` records that the role has no seeded permissions. The
seller surface is therefore structurally present and functionally empty. This is
a server task, not an app task.

**D-1 · Bundle IDs reused.** This app uses `in.brandcentral.retailops` on both
platforms — the same IDs as the archived `mobile/` app. That app never built
successfully and has no store listing, so the IDs were reused to avoid a second
permanent listing. If that app is ever shipped, change these before first
release.

**D-2 · No `google-services.json` reference.** The archived app pointed
`app.json → android.googleServicesFile` at a file that did not exist, which
fails the Android build at configure time. This app omits the reference
entirely. Add it only when the real file is supplied, via the EAS secret
`GOOGLE_SERVICES_JSON`, and keep the file gitignored.

**D-3 · Icons are placeholders.** Material Symbols is still an open decision
(04-component-library.md, P-10). Status and tab icons currently use short text
glyphs. Status is still conveyed as colour + icon + word, so the WCAG 1.4.1
requirement holds in the meantime.

**D-4 · Calls are not included.** `react-native-webrtc` and
`react-native-callkeep` need a development build and native configuration, and
the managed-workflow decision was to defer them. The archived `mobile/` app has
call and chat code that can be ported when calls reach Wave 3.

## 7. Relationship to `mobile/`

`mobile/` is the previous Expo app. It is **archived, not maintained** — its
build was broken (a CMake configure failure) and it pointed at a
`google-services.json` that does not exist. Its call/chat/WebRTC integration is
the one part worth porting when calls are scheduled.

Do not add features there. Do not copy from it without reading this file first.
