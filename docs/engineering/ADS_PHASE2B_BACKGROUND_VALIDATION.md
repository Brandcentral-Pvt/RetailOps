# Ads Phase 2B.2: durable background validation and searchable history

Baseline a39befe (PR #294). Migration 102 adds PREVIEW_QUEUED and VALIDATING job states plus validation attempt and completion metadata; existing READY and terminal history remain intact.

POST /api/upload/ads-imports now stores the privately staged source and returns 202 without parsing or catalog lookup. The primary worker has separate preview and commit polling loops. Preview claims use the same SQL transaction-owned application lock and lease-fencing mechanism as commits. CPU parsing runs in a separate Node worker thread; the parser retains exact source hash, original CSV record numbers, blank-row policy, decimal rules and first source ASIN mapping. It has a 120-second processing timeout and bounded heap. The database worker reauthorizes the owner and verifies the seller context/catalog before finalizing the preview in a fenced SQL transaction. VALIDATING never writes Ads facts. READY starts a fresh 24-hour confirmation window and resets the separate commit attempt counter. Invalid previews become REJECTED and clear staged bytes. Permanent access/context errors become FAILED. Transient errors requeue up to three attempts. Unclaimed preview and commit jobs can be cancelled; active jobs cannot. The confirmation pause stops commit claims, not validation. Pending capacity counts both queues and active workers.

The existing import modal shows actual scanned row counts, separate validation/commit states, polling and server-side history search by literal filename/job ID, status and authorized seller. READY retains explicit confirmation. No fake validation percentage. Existing Phase 1 diagnostic /ads-validate remains synchronous; the normal modal uses the durable route. Validation errors still retain the first 10,000 detected issues and indicate truncation; durable full-error streaming and retention policy are the remaining Phase 2B increment. The 32 MiB/200,000 data-row limit remains.

CI adds worker parsing at 100,000 and 200,000 synthetic rows, event-loop responsiveness, exact totals, malformed/blank records, SQL preview migration/history/authorization/recovery/cancellation/filter regressions and browser polling. These are synthetic parser measurements, not production database ingestion load tests. Production CSV financial reconciliation and actual gateway behavior remain unverified.

Deployment: all API workers must upgrade together; verify /api/health/ads-imports (098/099/101/102). Do not roll back to pre-102 code with pending preview jobs. No raw production reports or data are committed.
