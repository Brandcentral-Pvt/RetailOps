# Shared durable export workflow

Ads and GMS now use the same `reportExportJobs` queue engine and `reportExportJobsController` API factory, with separate report adapters, permission checks and database tables. The global Downloads drawer combines both durable job types with legacy downloads. Existing Ads jobs and legacy GMS downloads are retained. GMS configuration preserves current/custom/all dates, ASIN/seller grouping, daily/weekly/monthly matrix, CSV/XLSX and seller/search scope. The new GMS UI calls `/api/export/gms-jobs`; legacy `/api/export/start-gms` remains available for old clients.

Migration 106 creates `GmsExportJobs` and `GmsExportChunks`; startup runs the durable GMS worker independently of Ads. Both use leases, bounded retries, cancel, SHA-256 verified artifacts and retention. Default retention seven days, configurable with `GMS_EXPORT_RETENTION_DAYS` (1–30). Each module has separate queue and concurrency limits. GMS currently materializes its source facts and matrix; its new queue refuses more than 250,000 source facts including comparison history, rather than silently truncating. Ads capacity is not assumed to apply to GMS. Benchmark GMS matrix memory and large reports before raising this limit.

Deployment: run migration 106, restart the primary backend worker and deploy frontend together. Verify SQL lifecycle and browser suites; create current/custom/all-history Excel and CSV jobs; verify global drawer live stage, retry, cancellation, access revocation, download integrity and desktop Excel. Roll back the application if necessary, leaving additive tables intact. No production deployment or benchmarks are established by source commits.
