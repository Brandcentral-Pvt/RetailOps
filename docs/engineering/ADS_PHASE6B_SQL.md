# Ads Phase 6B: SQL reporting indexes

Migration 107 adds a date-leading rowstore covering index to the canonical fact table only when no usable date-leading index covers the required projection. It also conditionally adds a nonunique catalog owner/ASIN index if the two keys have safe bounded character types and no suitable existing index. No rows or existing indexes are removed. Duplicate catalog ownership remains explicitly detected by the current report query. ASIN drill-down and currency predicates now use native SQL parameter types.

The migration is additive and idempotent; run through the numbered migration runner. Index builds can consume disk, transaction log and locks; review table size, available capacity and maintenance timing before applying. Roll back the application without dropping indexes; index removal requires separate DBA review. No production index build has been performed.

CI runs actual SQL migration twice and compares full report payloads before and after; existing canonical coverage, export, duplicate catalog and authorization fixtures remain in place. The disposable benchmark `backend/testUtils/adsPhase6.index.sql.node.cjs` logs three end-to-end samples per scenario before and after index creation. Default 10k facts; use ADS_INDEX_BENCH_ROWS=100000 or 250000 with the disposable local SQL fixture. The benchmark compares identical report results, not just speed. Cache warming and plan compilation can affect measurements. Do not treat elapsed CI timing as production SLA evidence.

Before production rollout compare actual execution plans, logical reads, elapsed/CPU time, index storage and import write throughput with representative data. Catalog lookup indexing does not yet eliminate repeated per-fact lookup; a distinct-key materialization rewrite requires independent parity and load testing. Do not force SQL hints or add further indexes without evidence. Phase 6C is revision-aware caching; performance targets remain unverified.
