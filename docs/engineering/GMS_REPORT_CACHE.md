# GMS bounded report-block cache

## Baseline
PR 279 deployed per user. The verified CI run on its head passed backend and both mixed-catalog SQL fixtures. At 100k facts/51,667 catalog entries first/next page times were 1,010/604 ms; at 500k facts/58,333 catalog entries 3,053/1,887 ms. The first 500k query spent 2,959 ms in SQL and 94 ms composing rows. These are synthetic CI timings, not production measurements. The only GMS browser failure was the Ant Select option locator pointing to a hidden virtualized accessibility option.

## Design
Migration 096 creates three transactional revision rows and DML triggers on GmsDailyPerformance, Asins and Sellers. Facts invalidate on any write. Catalog changes invalidate on relevant Id/AsinCode/SellerId/Title differences; seller changes invalidate on Id/Name differences. Exact no-op metadata updates and irrelevant fields are skipped. Revisions commit or roll back with their source writes; SET NOCOUNT ON preserves import write counts. No historical financial rows are modified.

After existing authentication and permission checks, the report cache uses the current user ID, global/seller scope, normalized date window, seller selection, literal search, level, sort, page size and block index to form a fingerprint. One active Redis key per user, 60-second TTL, maximum serialized entry 1.5 MB, at most 200 matrix rows in a block (up to four adjacent pages), maximum selected window 90 days. The public API always returns at most 100 requested rows. SQL controls ranking and exact financial calculations. A cache hit requires a live committed revision match, with all three triggers enabled. A source revision change during computation discards the block and reruns the normal page query. Manual refresh and import completion bypass cache reads. A new sort/filter or distant page block may miss. Exports remain live authorized queries.

Redis disabled/unavailable, absent revision schema, missing/disabled trigger, empty scope, oversize block or long date range never serves an unverified entry. Redis calls have a 150ms wait budget and revision checks 750ms. Cache failure is not a report failure. X-GMS-Cache and Server-Timing expose hit/miss/bypass/refresh and timing details.

## Rollout and maintenance
Run migration 096 and verify trigger presence, SQL/Redis integration and GMS CI. Set GMS_REPORT_CACHE_ENABLED=false to bypass the cache if it is not improving real latency. Migration triggers still exist when application caching is disabled. The revision rows are shared transactional write points; assess lock waits, deadlocks and throughput under concurrent catalog sync/import before enabling broadly. The initial block miss reads more rows than a single page; do not claim faster cold opens without measurement. Keep Redis private, authenticated as appropriate and configured with a memory limit/eviction policy. No unbounded report history is cached.

Administrative TRUNCATE, bulk operations that suppress triggers, or manually disabling and reenabling triggers can bypass DML revisions. Keep caching disabled during such maintenance, invalidate/rotate revision rows before reenabling, and never disable triggers while relying on cached financial data. A failed migration leaves live SQL available. Apply deployment migrations in the usual controlled process; this PR does not run them against production.

## Tests and outstanding work
CI includes bounded block slicing, authorization fingerprint, revision race, cache-disabled/unavailable fallback, refresh and out-of-range page tests; real SQL trigger and import write-count/rollback checks; disposable Redis readback and adjacent-page measurements on 100k/500k fact fixtures. Correct the manager dropdown browser selector without weakening the scope assertion. No production tests have been run. Full-report materialization/ranking on a cache miss, all-history exports, permanent index/actual execution-plan review, production cold/warm p95, concurrent load benchmarks and OOS regression remain outstanding.
