# Ads Intelligence Phase 1A: canonical facts and read-only validation

Phase 0 is merged. The operator reports that the live Ads database is empty; that is not independent proof of its schema or content. This increment never deletes, renames, migrates or writes legacy AdsPerformance data. The new table is additive and not yet activated. It is intentionally a foundation PR, not a completed Phase 1 release.

## Included

- Migration 098 creates dbo.AdsProductDailyFacts, with all 63 source fields, nullable source metrics, DECIMAL(28,10) and BIGINT types, explicit seller/marketplace/report type/ASIN/date identity, seller FK, currency and source lineage. Raw source scales remain intact. Existing AdsPerformance and its consumers remain untouched. Migration is transaction-protected and checks the canonical column/key shape on repeat.
- The pure v1 validator accepts only UTF-8 CSV with 63 unique exact headers, independent of order. It handles CSV escaped quotes, BOM and strict calendar dates; preserves zero, null, signs and exact decimal totals; checks explicit ordered aliases; classifies exact/conflicting duplicates; rejects malformed values/unsupported precision; limits to 32 MiB/200,000 rows and first 100 issues. Every duplicate requires review, and validation summaries are for unique valid rows only.
- New permission-gated GET /api/upload/ads-validation-sellers and POST /api/upload/ads-validate: require adsreport_import; one explicit authorized seller; verify configured marketplace/currency against Sellers; temporary CSV cleaned up; no fact or catalog writes. Amazon India canonical labels map to INR. Ambiguous labels require operator-supplied ADS_SELLER_CONTEXT_JSON, keyed by internal seller ID, e.g. {"seller-id":{"catalogMarketplace":"Amazon","marketplace":"amazon.in","currency":"INR"}}. Do not guess a marketplace or currency from the filename. This is not verification of actual source ownership; the future writer must validate every catalog mapping and seller/account context.
- Legacy POST /api/upload/upload-ads now returns 409 before multipart processing. Import modal shows a validation-only flow and does not close automatically on success or imply that records were imported. The first seller list is independent of existing facts.
- Offline CLI: from backend, node scripts/validateAdsProductReport.js /path/report.csv. It prints private aggregate totals and coverage, not individual source records. Do not share raw output publicly or commit customer data.
- Dedicated Ads Phase 1 workflow, pure Node regression and disposable SQL integration tests. No production SQL execution in this PR.

## Remaining Phase 1B (activation gate)

Do not load production reports yet. Connect a transaction-safe canonical writer using validated rows, explicit account context and source lineage; reject conflicting seller/ASIN ownership before writes; define replacement/idempotency and concurrent-write semantics. Update all Ads Intelligence readers to the new fact table and owner-aware catalog joins; strictly authorize mixed seller selections; enforce currency-safe aggregates, explicit total sales/orders, conversion-based CVR/AOV, signed corrections and null/coverage semantics; fix target scope, pagination and date-range comparisons; isolate monthly legacy input. Adapt or explicitly retire unsafe legacy endpoints, dashboard consumers and export before enabling writes. Require real SQL and frontend checks plus reconciliation of the actual uploaded CSV. Phase 2 adds durable import jobs, confirm/cancel, error workbook and history.

The previous UI/API still reads legacy AdsPerformance; the new table deliberately contains no imported rows. Schema or validation success alone does not mean Phase 1 is complete. No GMS, OOS or Tasks runtime changes.
